# MinimalAgentV2：从 Hermes 蒸馏出的 Agent 执行引擎

## 1. 研究动机

Hermes 是一个面向真实任务的通用 Agent。它的能力并不只来自大语言模型本身，还来自模型调用、工具执行、上下文管理、预算控制、错误恢复和记忆持久化等一系列外围机制。直接阅读 Hermes 的完整实现时，核心执行逻辑容易被大量工程细节包裹，难以回答一个基础问题：一个能够持续完成任务的 Agent，最少需要哪些组成部分？

为回答这个问题，我没有尝试复制 Hermes 的全部功能，而是采用“核心原理蒸馏”的方式：先沿着一次任务的主执行链路识别关键状态和控制流，再将与具体平台、配置和业务无关的部分抽取出来，最后重新实现一个规模更小、边界更清晰的 Agent 框架 MinimalAgentV2。这个过程的目标不是替代 Hermes，而是通过可运行的重建验证对 Hermes 执行机制的理解。

## 2. 核心执行模型

MinimalAgentV2 将 Agent 的一次任务抽象为 `plan -> act -> observe` 的循环：

1. 根据用户输入和历史消息构建当前回合上下文；
2. 调用大语言模型，由模型决定直接回答或请求一个或多个工具；
3. 执行工具并将结果写回消息序列；
4. 将新的上下文再次交给模型；
5. 当模型返回最终文本、达到迭代上限或预算耗尽时结束任务。

这个抽象揭示了 Agent 的最小闭环：**模型负责决策，工具负责改变或观察外部世界，消息上下文负责在多轮执行之间传递状态，循环控制器负责限制任务的边界。** Hermes 中的预算控制、错误处理、上下文压缩和记忆同步等能力，都是围绕这个闭环增加的可靠性机制。

## 3. 模块化重建

在 MinimalAgentV2 中，我按照运行时职责对 Agent 执行过程进行拆分。核心模块及其职责如下：

| 模块 | 主要职责 |
| --- | --- |
| `ConversationLoop` | 组织一次完整的 Agent 执行过程 |
| `TurnContext` | 构建和维护当前回合所需的消息、凭证和运行状态 |
| `LoopController` | 管理迭代次数、预算和退出条件 |
| `LLMClient` | 封装模型请求、重试、退避和错误分类 |
| `ToolRunner` | 注册、调用工具，并将工具结果回填到上下文 |
| `MessageStore` | 保存和读取对话消息及执行过程中的状态 |

这种拆分并不是简单地把一个大文件分成多个文件，而是将不同类型的变化隔离开来。例如，更换模型服务商主要影响 `LLMClient`，增加工具主要影响工具注册和 `ToolRunner`，修改停止条件主要影响 `LoopController`，而不需要改动 Agent 的整体骨架。

拆分后的主循环可以概括为：

```python
def run_conversation(agent, user_message):
	context = TurnContext.build(agent, user_message)

	while LoopController.should_continue(context):
		response = LLMClient.complete(context.messages)

		if response.has_tool_calls():
			results = ToolRunner.execute(response.tool_calls)
			context.messages.append(results)
		else:
			return context.finalize(response.content)

	return context.timeout_result()
```

主循环保留 Agent 的控制流，而重试、预算、工具错误和消息存储等防御逻辑分别归属于对应模块。这样既能保留核心机制的可读性，也能使防御逻辑拥有明确的责任边界。

## 4. 研究成果

### 4.1 提炼了通用 Agent 的最小执行闭环

通过对 Hermes 核心执行路径的分析，我将复杂 Agent 系统中的主要控制关系归纳为“模型调用、工具调度、结果回填和循环终止”四个基本动作。这个模型解释了 Agent 如何从一次文本生成扩展为可以连续执行任务的系统，也为后续加入记忆、上下文压缩和安全控制提供了稳定的骨架。

### 4.2 完成了 Agent 执行引擎的模块化重建

MinimalAgentV2 将 Hermes 中分散在核心循环及其周边的运行时职责重新组织为独立模块，形成了可运行的 Agent 执行框架。重建过程使每个模块的设计动机都能够回溯到原系统中的具体问题，而不是将 Hermes 当作黑盒框架调用。

### 4.3 建立了从复杂源码到最小实现的验证路径

本项目形成了“源码分析 -> 核心机制蒸馏 -> 最小实现 -> 对照验证”的研究路径。与只阅读源码相比，重新实现迫使我明确回答以下问题：哪些代码是 Agent 循环不可缺少的核心，哪些代码属于可靠性、防御性或平台适配逻辑；这些逻辑应该由哪个模块负责；模块之间通过什么状态进行协作。

### 4.4 为后续 Agent 能力扩展提供了实验底座

在核心循环稳定后，可以在不改变基本控制流的情况下继续研究技能系统、Plan Mode、上下文压缩、记忆管理、工具并行执行和可观测性等问题。每一项能力都可以作为独立模块或实验变量加入，从而观察它对任务完成、执行成本和系统可靠性的影响。

## 5. 当前验证范围与不足

MinimalAgentV2 的当前成果主要证明了核心执行机制可以被抽取并重新组织为一个可运行框架。它目前仍属于个人研究和实验项目，验证场景以本地使用和功能测试为主，尚不能据此宣称已经达到 Hermes 或生产级 Agent 系统的可靠性、并发能力和规模要求。

后续需要补充的验证包括：不同工具数量和失败模式下的执行测试、模型请求超时与重试测试、长上下文下的压缩效果评估、任务完成率与成本统计，以及多任务并发场景下的资源隔离测试。只有完成这些实验，才能进一步讨论模块化设计对可靠性和可维护性的实际影响。

## 6. 阶段性结论

MinimalAgentV2 的价值不在于重新实现了一个更大的 Agent，而在于把复杂系统中难以直接观察的执行原理变成了一个可阅读、可运行、可修改和可验证的最小系统。它是对 Hermes 源码理解的一次工程化验证，也是后续研究 Agent 上下文管理、工具系统和可靠性机制的实验基础。
