# 第二章 Agent 记忆：业界方案剖析与生命周期规则引擎设计

## 1. 研究动机：执行闭环之外，agent 还缺什么

第一章建立了 `plan -> act -> observe` 的执行闭环：模型负责决策，工具负责改变或观察外部世界，消息上下文负责在多轮执行之间传递状态。这个闭环能回答"agent 如何完成一次任务"，但有一个问题它没有回答：**跨任务的状态从哪来？**

一个没有记忆的 agent 有两个明显缺陷：

1. **每次会话从零开始**。用户说过的话、踩过的坑、形成的偏好，在会话结束后全部丢失；下一次任务，agent 会重复问用户已经回答过的问题。
2. **上下文窗口是有限的**。任务变长后，历史消息无法全部塞进上下文，agent 只能看到最近的一小段，更早的信息被截断。

这不是个人观察。2026 年发表的 Agent 记忆领域综述（*Rethinking Memory Mechanisms of Foundation Agents in the Second Half: A Survey*，arXiv:2602.06052，收录 2023Q1–2025Q4 共 218 篇工作）给出的判断是：AI 进入"下半场"后，长程任务的核心瓶颈就是记忆——**上下文会爆炸，agent 必须持续积累、管理、选择性复用跨长交互的信息**。

于是第二章研究 agent 记忆系统，拆成两个问题：

1. **全景**：业界主流方案是怎么设计的？各自的核心机制和取舍是什么？
2. **判断力**：一条信息值不值得记、该留多久、该放哪？这个判断怎么做、能不能被审计？

第一个问题通过逐个解剖四个代表性方案回答（Mem0、Letta、Graphiti、Hermes 内置记忆），第二个问题通过提出一套"生命周期规则引擎"的设计来回答。

## 2. 四个代表性方案

### 2.1 Mem0：LLM 提取事实的语义记忆层

Mem0 是给 agent 加"记忆层"的开源项目（YC S24 孵化，前身是 MemGPT）。它不是向量数据库，也不是 RAG 框架，而是架在 LLM + 向量库之上的一层**记忆语义层**。

**记忆形态**：三层分工存储。向量库存提取后的事实条目（检索主战场，30 种向量库可换）；图库存实体关系（可选，补充向量而非替代）；SQLite 存原始对话消息 + 记忆历史（可追溯、审计）。关键设计：**原始对话也落库**——即使 LLM 没提取出任何事实，对话也留痕，提取层出问题有原始层兜底。

**写路径**：`add()` 走五个 Phase，核心是 Phase 2 的 LLM 提取。把 [新消息 + 已有记忆 top10 + 最近 10 条消息] 一次喂给 LLM，输出三类指令而不是一条追加：

- `ADD`：全新事实，直接写入
- `UPDATE`：与已有记忆冲突/过时，覆盖旧条目（用户先说"住北京"后说"搬去上海"，结果是改，不是并存两条矛盾记忆）
- `DELETE`：用户明确否定/改主意，删除旧记忆

这个"提取 + 对账"是 Mem0 与普通向量记忆的本质区别：**存原文就没有"更新"概念，只有提取成结构化事实，才能做增改删**。

**读路径**：多信号混合打分（`semantic + bm25 + entity_boost`），且**语义分先过阈值门槛才进入融合**——语义上不相关的候选，BM25/实体加成拉不回来。这是"先筛后加"，不是加分排序。

**关键设计决策**：提取事实不存原文（记忆密度）；写时检索已有记忆（解决矛盾，代价是每次 add 多一次向量检索 + 一次 LLM 调用）；user/agent/run 三层作用域（记忆不是全局一锅粥，防止跨主体串记忆）。

**结构性短板**：判定主体是 LLM，说不清"为什么记这条"；无生命周期分层，只有可选的过期隐藏；每次写入成本高（一次 LLM 调用 + 一次检索）。

### 2.2 Letta：agent 自我编辑的记忆文件

Letta（前身 MemGPT，2025 年重写为 letta-code）是"有状态的 agent 运行框架"，走的是另一条路线：**记忆是文件，agent 在对话中主动编辑自己的记忆**。

**记忆形态**：Memory Blocks（记忆块）——一组常驻上下文的文本块，`persona`（agent 的自我认知）和 `human`（agent 对用户的了解）。关键点：这些块直接拼进系统提示词——记忆不是"查的时候才想起来"，是**每轮都在上下文里**。

**写路径**：5 个记忆工具（`memory` / `memory_apply_patch` / `memory_insert` / `memory_replace` / `memory_rethink`），agent 在对话中主动调用。主力工具对记忆文件做 add/update/delete 三类操作，**每次写入都是一次 git commit**。整个记忆目录（`.letta/`）是 git 仓库，可同步到私人 GitHub——记忆跟代码一样可版本回滚、可异地同步。

**读路径**：persona/human 块常驻（记忆 ≈ 提示词，天然"想起"）；体量大、不常用的走全文搜索（`/search`）和内置 recall 子代理。

**关键设计决策**：记忆用文件 + git 而不是数据库（版本化、可审计、可移植，代价是不是为检索设计的存储）；agent 自我编辑而不是系统提取（记忆决策发生在对话内，可被用户看到、纠正——这是"主体性"的业界极致）；记忆常驻而不是 RAG 按需检索（身份和用户偏好永远在线）。

**结构性短板**：git 记录了"改了什么"，但没有"为什么改"——判定仍是 LLM 的隐式判断；生命周期靠定期"做梦"（dreaming）事后反思，没有先验的过期机制。

### 2.3 Graphiti：带时间轴的知识图谱

Graphiti 是 Zep 的开源核心（30.3k stars），做的是"时间感知记忆"：实时增量构建知识图谱，每条关系带双时间轴，能回答"当时的事实是什么"。

**记忆形态**：三层节点——Episodic 层（原始 episode 原文）、Entity 层（去重后的实体）、Community 层（聚类社区 + LLM 摘要）。灵魂是 EntityEdge（边）：

```python
class EntityEdge(Edge):
    fact: str                      # 事实陈述（"X 于 2024 年收购了 Y"）
    fact_embedding: list[float]    # 事实的向量（检索按边检，不是按节点）
    valid_at: datetime | None      # 事实开始为真的时间
    invalid_at: datetime | None    # 事实停止为真的时间
    expired_at: datetime | None    # 系统发现并失效这条边的时间
    reference_time: datetime | None  # 产生这条边的 episode 的时间戳
    episodes: list[str]            # 引用这条边的来源 episode id（可追溯）
```

**写路径**：`add_episode` 增量流水线（取前情 → 提取实体 → 对齐合并 → 提取+解析边 → 属性提取 → 存原文 → 更新社区）。两个区别于普通 GraphRAG 的关键：**增量不重建**（图随对话实时长大，GraphRAG 是批处理建图）；**边失效**（新信息与旧事实冲突时，旧边被打上失效时间——图自己会"遗忘"，不留矛盾事实）。

**读路径**：edge/node/episode/community 四个 scope × 关键词/向量/图遍历三种手段的混合检索，加 MMR 重排和时间过滤。**检索的单位是边（事实）而不是节点**——"A 和 B 有什么关系"直接命中。

**关键设计决策**：时间轴放在边上而不是节点上（事实关系才是会变的）；检索按事实（`fact_embedding` 让"语义相似的事实"可检索，这是图 + 向量融合的关键）；增量 + 失效而不是重建（对话是流式的，图必须实时可用）。

**结构性短板**：提取和失效判定都靠 LLM（不可审计）；依赖图数据库（Neo4j/FalkorDB），部署重，不适合教学级项目。

### 2.4 Hermes 内置记忆：有界双文件

Hermes（我蒸馏第一章的原系统）自己的记忆系统是最朴素的一档：**两个有界文本文件**——`MEMORY.md`（agent 自己的笔记）和 `USER.md`（用户画像），容量上限 2200 字符 + 1375 字符。

**记忆形态**：两个有限长度文本文件，单条记忆用 `memory` 工具读写（add/replace/remove），写满时提示合并（replace 合并重叠条目）。

**双状态设计**（关键中的关键）：系统提示词里的记忆是**会话开始时冻结的快照**，永不中途改（保证 prompt caching 稳定）；工具调用修改的是实时状态，落盘后模型能看到"我改成了什么"。两套并行，互不干扰。

**防投毒**：加载时逐条扫描注入模式（promptware），命中就把该条替换成占位符——记忆文件里被塞了"忽略以上指令"之类的恶意文本，注入发生在文件层，快照层直接屏蔽。

**写路径**：对话中模型调 `memory` 工具直接写；每 10 轮（可配）fork 一个后台反思 agent，重放会话判断"用户透露了什么值得记"，调 memory 工具写入——**"记什么"由后台反思 agent 判定，不挡对话**。

**关键设计决策**：有界 = 强制蒸馏（写满必须合并，容量限制本身就是"什么值得留"的过滤器）；零依赖零部署成本；防投毒 + 冻结快照的工程细节扎实。

**结构性短板**：无检索（全量常驻，超过容量只能合并删除）；无时间维度（记不住"什么时候说的"）；被动（判定靠后台反思，agent 不能主动改）。

## 3. 横向对比：生命周期三维度

四家方案摸完，需要一个统一框架来评判它们。我采用的框架来自"知识生命周期"视角，三个维度回答同一个问题——**这条信息现在该放哪、留多久**：

| 维度 | 含义 | 对应问题 |
|---|---|---|
| **属性（先验）** | 出生时的类型决定活多久 | 人名、合同天生该长期存；天气、热搜天生该过期 |
| **频率（后验）** | 重要的东西会反复出现 | 反复出现 = 权重高 = 从临时区升到长期区 |
| **有效期** | 现在过没过期 | 过期自动忽略，上下文利用率靠保质期 |

三条合起来用，是**用频率检验属性猜得对不对**：属性该长命但从来没人用 → 降级冷藏；属性该短命但反复出现 → 升级（它正在变成长周期问题）。先验给初判，后验给修正，后验可以推翻先验。

用这个框架回看四家方案：

| 维度 | Mem0 | Letta | Graphiti | Hermes 内置 |
|---|---|---|---|---|
| 属性（先验分层） | ❌ 无分层，仅可选过期隐藏 | ❌ 无 TTL | ⚠️ 时间轴在边上，但无类型分层 | ❌ 有界即变相 TTL，无显式分层 |
| 频率（后验修正） | ❌ 无（只能靠 UPDATE 对账） | ⚠️ dreaming 定期反思，事后无数据驱动升级 | ❌ 无 | ⚠️ 后台反思，无数据驱动升级 |
| 有效期 | ⚠️ 仅 expiration_date 隐藏 | ❌ 无 | ✅ valid_at/invalid_at 双时间轴（最强） | ⚠️ 写满强制合并（变相淘汰） |
| 判定主体 | LLM（不可审计） | LLM（git 有"改了什么"无"为什么改"） | LLM（提取/失效都靠模型） | LLM（后台反思） |
| 冲突处理 | UPDATE/DELETE（LLM 判，黑盒） | 自我编辑（agent 判） | 边失效（LLM 判） | 合并（人工/模型） |

这张表揭示了一个共性：**四家方案的判定主体都是 LLM，没有任何一家把"取舍判断"做成可审计的确定性规则**。记忆系统的失败模式——记错、记矛盾、误删——发生时，四家都回答不了"为什么"。

同时各家都有值得抄的点：Mem0 的"提取事实 + 写时对账"、Letta 的"记忆即文件 + git 审计"、Graphiti 的"时间轴 + 来源可追溯"、Hermes 的"有界强制蒸馏 + 防投毒"。

## 4. 设计提案：生命周期规则引擎

### 4.1 设计动机：为什么不用 LLM 判

业界方案全部交给 LLM 判断"什么值得记"，这条路有一个根本问题：**记忆事故发生时，怎么回答"为什么"？** "这条记忆为什么进了长期层？"——LLM 给不出答案。判断结果无法回放、无法审计、无法修正。而记忆系统最怕的就是不可追责：记错了，你甚至不知道它是怎么错的。

因此设计的第一原则：**可解释性是记忆系统的底线**。判断用规则引擎——确定性分支，任何一条记忆都能回放完整的规则链。出了事故，回答"为什么"→ 找到规则 → 改规则。LLM 的位置从"法官"降级为"司法解释"：只处理规则拿不准的灰色地带（比例控制在约 90% 规则 / 10% LLM）。

### 4.2 规则锚在知识生命周期上

规则不能是拍脑袋的（"我觉得身份重要"），需要一个统一判据。我借用的判据是：

> **变更成本 ≈ 生命周期 ≈ 重建成本**

一句话：知识的变更成本越高，越值得长久存。家乡（物理不可变）、职业（转换成本高）、设计目标（推翻 = 全盘重来）一眼长命；丢了重建代价大的知识必须深存——"存那个丢了最心疼的"；八股短命，因为考纲变更成本为零。落到规则上就是类型查表：身份/原则 → 长期；稳定偏好 → 长期；具体技术用法 → 短期（带 TTL）；临时状态 → 最短命。

### 4.3 分层靠淘汰策略，不靠预测

记忆分层（L1 临时 / L2 工作 / L3 长期）最容易踩的坑是：想靠预测一次分对。但预测总会错——误杀一条长命知识的代价，远大于多存一条短命知识。

所以原则是：**以使用定生死，不以预测定生死**。分层不是靠预测，是靠每层不同的淘汰策略：

- L1：会话结束即过期，不值得存
- L2：带 TTL，到期**降级 + 对账提示**，绝不静默删除（防误杀）
- L3：几乎不淘汰，仅显式纠正可降级

并留复活机制：L2 的记忆被频繁召回（≥3 次/30 天）自动升级 L3——初判错了没关系，使用反馈会修正。判断器给的是先验，使用验证给的是后验，**后验永远有权推翻先验**。

### 4.4 规则集（12 条）

**硬分流 4 条**（命中即短路，直接定层）：

| 规则 | 内容 | 判定 |
|---|---|---|
| R1 | 知识类型查表 | 身份/原则/稳定偏好 → L3；具体用法 → L2+TTL；临时状态 → L1 |
| R2 | 变更成本判据 | 离底层约束近 / 重建代价大 → L3；可重新获取 → 降级 |
| R3 | 来源等级门槛 | 用户亲口说且是身份/原则 → L3 候选；纯工具观察无确认 → 最多 L2 |
| R4 | 显式用户反馈 | 置顶 → L3；归档 → 出局/降级 |

**打分 5 条**（灰色地带累计 lifetime_score，0–100）：

| 规则 | 条件 | 分值 |
|---|---|---|
| S1 | 类型接近身份/原则/稳定偏好 | +30 |
| S1 | 类型接近具体用法 | +10 |
| S2 | 变更成本高（重建代价大） | +30 |
| S2 | 变更成本低（可重新获取） | -20 |
| S3 | 来源 = 用户亲口说 | +20 |
| S3 | 来源 = 模型推断 / 工具观察 | +5 |
| S4 | 内容是"为什么"（原理/约束） | +15 |
| S4 | 内容是"怎么做"（步骤/命令） | +5 |
| S5 | 临时状态 | -40 |
| S5 | 带明确时效（"这周"/"项目期间"） | -20 |

阈值：**≥80 → L3 长期；40–79 → L2 工作（带 TTL）；<40 → L1 临时**

**后验修正 3 条**（运行时，使用反馈推翻初判）：

| 规则 | 事件 | 动作 |
|---|---|---|
| P1 | 召回 ≥3 次/30 天 | L2 → L3 自动升级（复活机制） |
| P2 | L2 超 TTL 未召回 | 降级 L1 + 对账提示（不静默删除，防误杀） |
| P3 | 用户纠正 | 覆盖一切先验，按纠正后内容重新判定 |

优先级：**显式反馈（R4/P3）> 来源门槛（R3）> 类型查表（R1/R2）> 打分（S1–S5）**。冲突原则：用户说什么就是什么——规则引擎的职责是猜，用户反馈是事实，事实永远压过猜测。

### 4.5 提取层与判断层分离

规则引擎能判断的前提是：输入已经是"一条独立的事实"。但对话原文是一大段话——"我是 Java 后端，之前做流批一体，最近在学 RAG，这周五交周报"，里面是 4 条生命周期完全不同的记忆。

**切句（提取）和分层（判断）是两件事**：切句需要语义理解（中文口语一逗到底，必须读懂内容才知道哪几个事实绑在一起）——LLM 的强项；分层需要确定性（同一套规则永远给同一结果，可审计）——规则引擎的强项。所以各干各的：

```
对话原文 → LLM 提取（原子事实清单 + 类型标签）→ 规则引擎分层 → 落库
```

切分粒度一条硬原则：**一条记忆只能有一个生命周期**。如果一条内容里混着长命的（"我是 Java 后端"）和短命的（"这周五交周报"），规则引擎就没法判。提取时机也刻意低频：不每条消息都切，每 N 轮对话做一次批量提取（background review），与"事后批量对账"接上——收尾时给用户"本次我记住了这些"清单确认。

### 4.6 与业界方案的对应关系

这个设计不是从零发明，是对四家方案短板的批判性升级：

| 业界机制 | 我的设计对应 |
|---|---|
| Mem0 的 UPDATE/DELETE（LLM 判，黑盒） | P3 用户纠正覆盖的自动化弱化版——但 P3 是确定性规则，可审计 |
| Mem0 的提取层 | LLM 只做提取（切事实），分层交给规则 |
| Letta 的 dreaming 反思 | P1 复活机制的灵感——但 P1 有数据判据（≥3 次/30 天），不是 LLM 隐式判断 |
| Letta 的 git 审计 | rule_chain（每条记忆落库时记录命中的规则编号，如 `["R1","R3"]`）——回答"为什么记" |
| Graphiti 的时间轴 | TTL（先验）+ 后验修正——Graphiti 的四时间字段是查询能力，教学级项目用 TTL 更轻 |
| Hermes 的有界双文件 | L1/L2/L3 三层存储的思想来源——有界强制蒸馏是对的，但分层要显式 |

## 5. 本章小结

本章的贡献有三层：

1. **全景认知**：解剖了记忆领域四个代表性方案（LLM 提取派 Mem0、自我编辑派 Letta、时间感知派 Graphiti、有界文件派 Hermes），各自的记忆形态、写路径、读路径、关键决策和短板。
2. **统一框架**：提出生命周期三维度（属性/频率/有效期）作为评判记忆系统的标尺，并据此指出业界共性短板——判定主体全是 LLM，取舍判断不可审计。
3. **设计提案**：提出生命周期规则引擎（12 条规则 + 提取/判断分离 + rule_chain 可审计），作为对业界短板的批判性升级；设计已成文，实现列为后续工作。

一句话收束：**记忆管理的难点不在"能存多少"，在"能不能快速判断出什么值得反复用，再按它的类型和用法决定放哪、留多久"——而这个判断必须可审计。** 业界把判断交给 LLM 黑盒，我用规则引擎把它变成"可回放、可修正、可追责"的确定性决策。
