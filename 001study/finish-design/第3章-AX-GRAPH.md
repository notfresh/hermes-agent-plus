# 第三章 AX-GRAPH：大项目源码阅读的方法与工具

## 1. 研究动机：17 万行的 Hermes 为什么难读

第一章的起点是 Hermes 难读——防御性机制太多，核心执行逻辑被大量工程细节包裹。但当时采取的是"蒸馏"解法：抽出一个最小版来理解原理。这个解法适合回答"核心机制是什么"，却解决不了另一个问题：**当我要继续读 Hermes 的其他部分、或者迁移改造它时，怎么定位"某个功能在代码库的哪里、依赖谁、改一处会波及谁"？**

大项目阅读有三个具体痛点：

1. **目录是摆设**。Hermes 的 `agent/` 目录平铺 156 个文件，只有 4 个小包；内部 266 条依赖边，密度 1.71 边/文件。靠目录树读代码，只能看到一堆名字，看不出谁跟谁抱团。
2. **入口声明 ≠ 入口实现**。`console_scripts` 指向 `hermes_cli.main:main`，不是直觉上的 `cli.py`——顺着直觉找入口会走错路。
3. **功能是横切多模块的**。"skill 加载"这个功能横跨 `agent/` 和 `tools/` 多个目录，任何单一目录视角都看不到全貌。

这个痛点不限于 Hermes：任何达到一定规模、由 coding agent 或团队持续生成的项目都有同样的问题。于是第三章的目标是：**造一个方法和工具，把"读大代码库"从"大海捞针"变成"按图索骥"，并让它能迁移到其他开源项目**。

## 2. 方法：把代码库变成三层图

核心方法：用图描述代码库，分三层粒度，每层回答一类问题。

| 层 | 回答的问题 | 节点 kind | 关系 |
|---|---|---|---|
| Layer-1 源码级 | 代码分布在哪 | module / file | CONTAINS（归属）、DEPENDS_ON（耦合，weight=import 次数） |
| Layer-2 簇级 | 谁跟谁抱团 | cluster / subpackage | CONTAINS（隐式簇） |
| Layer-3 功能级 | 功能怎么实现 | feature / function | REALIZED_BY（功能→函数）、CALLS（函数→函数，带调用点行号） |

**为什么分三层而不是一张大图**：一层图把所有节点平等铺开，等于没分层。源码级解决"东西在哪"，簇级解决"结构怎么组织"，功能级解决"一个功能怎么跑通"——粒度不同，回答的问题不同。功能级尤其关键：**feature 是横切多模块的**（skill-load 横切 agent/+tools/），模块级的 CONTAINS 表达不了，必须单独一层。

存储用 TOML（机器可解析、可直接手编、diff 友好），每层一个文件，查询时自动合并。节点带 `path` + `files+lines`（文件:行号），函数级节点 id 带 `文件::函数:行号`，可以上下钻取。

**两条铁律**：

1. **关系必须实测，不编造**。DEPENDS_ON 的 weight = import 静态分析实测计数；函数行号当次 grep 实测；测不了的标"待验证"。图的价值建立在真实之上，编一条边就污染一片查询。
2. **手动挡优先**。构建图的过程 = 读码学习的过程。不引入 tree-sitter/MCP/SQLite 等全自动建图体系——自动建图能出图，但读图的人没读过代码，图是死的。同类项目（colbymchenry/codegraph）已调研，明确不采纳。工具只做查询和校验，图的生长靠人读码、人确认。

## 3. 架构观量化：函数纯净 + 高内聚低耦合

我对代码架构的理解有两条：**函数尽量纯净**（单函数质量），**模块高内聚低耦合**（模块间结构）。AX-GRAPH 把这两条变成了可查询、可量化的指标。

### 3.1 函数纯度：找"干净函数孤岛"

`purity.py` 把函数分成三档：

- **L0 严格纯**：只用参数 + 局部变量
- **L1 工程纯**：读外部常量/配置，但无副作用（如读数据 + 打印输出的展示型函数）
- **非纯**：写外部状态 / 有副作用调用

L0 + L1 = 干净，可以单独阅读。价值在于：**在巨型代码库里找"干净函数孤岛"降复杂度**——先读干净的部分建立熟悉度，再碰有副作用的。

判定规则有讲究：局部加工（改自建局部对象）≠ 外部副作用（改参数/全局），前者不降级——否则全是加工局部数据的纯函数被误杀。调用者传递：A 调 B、B 非纯 → A 非纯（依赖图里实测 CALLS 边，不猜）。print 不算副作用（控制台输出不影响数据加工）。

### 3.2 高内聚低耦合：CONTAINS 与 DEPENDS_ON

- **CONTAINS = 内聚**：归属关系，"容器在前，单向"。
- **DEPENDS_ON = 耦合**：weight = 模块间 import 次数（实测）。weight 越大，耦合越紧。

这套度量能读出目录看不出来的结构结论。例如 Hermes：`hermes_cli` 被依赖 970 次，全库第一——它根本不是 CLI 薄壳，而是核心底座；`agent/` 平铺 156 文件，内部依赖密度 1.71 边/文件（比 cron 的 0.73 高得多），说明它"抱团"但靠命名模式 + 依赖网维系，不靠目录。

## 4. 工具实现：graph_query.py

`graph_query.py` 是查询与校验工具，设计目标是"低摩擦读图"：

- **模糊匹配链**：`%` LIKE 通配（id + path 双字段）→ 精确 → 包含 → difflib 近似。错拼也能捞回。
- **调用链查询**：`-c` 正向调用链（谁调了谁）、`-r` 反向链（改 X 会波及谁）、可共存。
- **层级过滤**：`-l` 按层过滤，只看想看的粒度。
- **`--validate` 分级校验**：Error（悬空边 / path 不存在 / 行号非 def/class，必须修）+ Warning（缺 desc 等历史欠账，可暂缓）。分级是为了让旧图欠账不淹没新加的节点。
- **节点详情**：`-b <id>` 打开编辑器写读码笔记（git commit 式工作流），存成独立的 NodeDetails.toml——节点是骨架，读码笔记是血肉。
- **多 base 体系**：`--base` 切换项目图/单文件图，`--new-base` 建新库。每个 base 的 `base.toml` 带 `repo` 字段（path 解析基准）——**设计上天然支持指向不同仓库**，这是迁移到其他开源项目的基础。
- **`--file` 单文件图**：对任意 Python 源码文件 AST 自动建图（顶层函数/类 + 函数间 CALLS 边）。分析范围不被主图锁死，任何源码都能建图——工具可以分析自己。

## 5. 验证：Hermes 案例

三层图在 Hermes（17 万行，研究副本）上建成：Layer-1 41 节点 / 101 边，Layer-2 29 节点 / 31 边，Layer-3 两张功能图（skill-load 22 节点 / 36 边、skill-startup 25 节点 / 61 边），全图合并 148 节点 / 304 边 / 0 悬空。

建图过程产出了靠通读代码很难得到的发现：

1. **hermes_cli 是核心底座不是 CLI 薄壳**：被依赖 970 次全库第一，agent(188)/tools(142) 反向大量 import 它——名字名不副实，17 万行有原因。
2. **真实核心簇 = hermes_cli + agent + tools 三巨头**：互相 import 上百次，强耦合，并非"接口层→核心层"的单向依赖。
3. **隐式簇**：`agent/` 平铺 156 文件，挖出适配器簇（6 个 *_adapter）、共享底座簇、凭证簇、提示词安全簇——**簇靠命名模式 + 依赖网维系，不靠目录，agent 不能按目录读，要按依赖网读**。
4. **功能级链路**：skill-startup 功能链挖出 23 条 CALLS（全带调用点行号），关键发现是**启动路径的"加载 skill"= 索引注入（名+描述+分类），不是读全文**——SKILL.md 全文是运行时 skill_view 才读。这种结论只有追踪到函数级才能得出。
5. **多语言盲区教训**：只统计 .py 会漏掉 1600+ TS/TSX/RS 文件（前端应用层），分布图必须全语言覆盖。

验证结论：三层图 + 实测铁律能在大代码库中定位功能实现路径、识别结构问题、产出可查询的读码笔记，且查询工具让这些发现可以反复检索而不是散落在一次性的阅读过程里。

## 6. 与第二章的关系：时间维度 vs 空间维度

第二章（记忆管理）和第三章（代码图）表面上是两个领域，底层是同一个思想：**分层 + 取舍**。

- 第二章把信息按"值不值得长期留"分层（L1 临时 / L2 工作 / L3 长期），用生命周期三维度做取舍。
- 第三章把代码按"值不值得细看"分层（源码分布 / 隐式簇 / 功能链），用实测关系做取舍。

区别在维度：**第二章管时间**（一条信息现在该放哪、留多久），**第三章管空间**（一段代码在哪里、依赖谁、波及谁）。两者都是"把无差别的信息流组织成有结构、可查询的形态"——这是上下文工程的两种应用。

## 7. 现状与未来

**当前状态**：三层图 + 查询/校验/纯度工具已建成，Hermes 单一案例验证通过。原型定位（2026-08-28 定）：手动挡，构建图的过程即读码学习的过程，不引入全自动体系。

**后续工作**：

1. **迁移其他开源项目**：多 base 机制已支持（repo 字段指向不同仓库），尚未实战。下一步选一个目标项目（如 Kimi Code 或 Claude Code 的源码），完整走一遍建图流程，验证方法可迁移性。
2. **工程质量分析 skill（愿景）**：基于 AX-GRAPH 底座写一个软件工程质量分析 skill，形态为**半自动诊断**——工具输出图数据信号，人/LLM 结合上下文下结论，而不是自动生成诊断报告。可诊断的维度包括：耦合严重模块（DEPENDS_ON weight 分布）、上帝模块（入度/扇出超高）、内聚度（隐式簇与目录结构不一致）、函数纯净度（L0/L1 占比、非纯集中区）、死代码（孤立节点）、影响面（反向 BFS）、架构分层违规（跨层依赖）。当前状态：愿景规划，尚未实现。
3. **开源 issue 理解**：issue 通常涉及多个功能链。用图把 issue 映射到功能链 → 涉及文件 → 影响面（反向 BFS），让"读 issue"变成"读图"，降低理解开源项目的门槛。
4. **定时巡航巡检（远期设想）**：更远期的形态是把"分析"从按需触发变成定时巡航——cron 驱动 agent 周期性跑图数据 + 质量分析，自动巡检代码库、发现新问题（新增耦合、纯度下降、死代码堆积），定时产出巡检报告。参考我在 Hermes 上已有的定时探索实践（任务 001/002：cron 驱动 agent 周期探索 + 投递报告）。这是远期方向，现阶段不实现。

## 8. 本章小结

本章的贡献有三层：

1. **方法**：提出三层图（分布 → 隐式簇 → 功能链）描述代码库，铁律是关系实测不编造、手动挡 = 读码学习。
2. **工具**：graph_query.py + purity.py 把"函数纯净、高内聚低耦合"的架构观变成可查询、可量化的指标，多 base 设计为多项目迁移铺路。
3. **验证**：Hermes 17 万行案例产出 148 节点 / 304 边 / 0 悬空的图，发现核心底座 970 次依赖、隐式簇结构、启动链路"索引注入非全文读取"等通读难见的结论。

一句话收束：**读大代码库的困难不在"字不认识"，在"不知道哪些字值得读、它们之间什么关系"——AX-GRAPH 把这个问题从"凭感觉"变成"按图索骥"。**
