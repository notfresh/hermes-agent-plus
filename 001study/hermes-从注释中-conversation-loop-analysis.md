# Hermes Agent 对话循环核心机制技术分析

## 概述

`conversation_loop.py` 中的 `run_conversation` 方法是 Hermes Agent 框架的核心引擎，负责执行完整的对话流程并支持工具调用。本文基于该方法的代码注释，系统性地分析其架构设计、关键机制和错误恢复策略。

该方法经历了数千行代码的演进，积累了大量的防御性编程实践和边界情况处理，理解这些设计决策对于掌握 Agent 框架的开发模式具有重要参考价值。

## 一、对话循环的总体架构

### 1.1 方法职责

`run_conversation` 方法接收用户消息，执行多轮 API 调用直到获得最终响应或达到迭代上限。其核心职责包括：管理对话历史、构建 API 请求、处理模型响应、执行工具调用、处理各种错误和边界情况，以及维护会话状态。

整个循环的设计遵循"防御性编程"原则：即使面对异常的 API 响应或网络问题，框架也要尽可能恢复并继续执行，而不是直接失败。

### 1.2 主循环结构

```python
while (api_call_count < agent.max_iterations 
       and agent.iteration_budget.remaining > 0) or agent._budget_grace_call:
    # 每次迭代的完整处理流程
```

循环的退出条件由两个因素共同决定：最大迭代次数和迭代预算。这种设计允许框架在预算耗尽时给模型一次"宽恕调用"（grace call），确保即使在预算紧张的情况下也能产生一个可用的响应。

## 二、每次循环的初始化阶段

### 2.1 Prologue：构建turn上下文

代码注释明确指出，所有单次turn的设置工作都集中在 `build_turn_context` 函数中，包括：标准输出输入保护、重试计数器重置、用户消息清理、待办事项和提示的激活、系统提示的恢复或构建、压缩前准备、`pre_llm_call` 插件钩子、外部内存预取，以及崩溃恢复持久化。

这种集中化的设计使得代码职责清晰，每个组件专注于自己的任务，同时通过 `agent` 对象的可变状态在组件之间传递数据。

### 2.2 凭证池刷新计数

每次turn开始时，框架会重置凭证池刷新计数：

```python
agent._auth_pool_refresh_counts = {}
```

这个设计解决了一个微妙的问题：当上游持续返回 401 错误时，单一凭证的刷新可能会"成功"（因为刷新函数本身没有报错），从而陷入无限循环。通过限制同一凭证的连续刷新次数，框架可以在必要时切换到备用凭证。

### 2.3 Codex App Server 运行时

对于启用了 Codex 应用服务器模式的情况，框架会将整个turn交给子进程处理，终端操作、文件操作和补丁应用都在 Codex 内部运行。这是一种可选的运行时模式，通过 `agent/api_mode == "codex_app_server"` 判断。

## 三、消息准备与预处理

### 3.1 API消息副本的构建

在发送 API 请求前，框架会从对话历史构建专门的 API 消息列表。这是一个关键的架构决策：原始的对话历史（`messages`）保持不变，而 API 副本（`api_messages`）用于实际请求。这种分离确保了：

1. 原始历史用于 UI 显示和会话持久化
2. API 副本可以进行各种清理和转换而不影响原始数据
3. 某些字段（如 reasoning）需要特殊处理以兼容不同 provider

### 3.2 角色交替修复

框架会主动修复损坏的角色交替序列，例如 `tool → user` 或 `user → user` 的尾部。这种情况可能发生在空响应脚手架被剥离后、新的用户消息出现在孤立工具结果之后。大多数 provider 在遇到这种异常序列时返回空内容，如果没有这个修复，对话会陷入无限空响应重试循环。

### 3.3 临时上下文的注入

有两类临时上下文在 API 调用时注入：

**第一类是外部记忆预取和插件 pre_llm_call 钩子**，它们将上下文注入到当前turn的用户消息中。这些都是 API 调用时的一次性操作，原始消息从不被修改（除了 api_content 戳记），因此不会泄漏到干净的记录内容中。

**第二类是临时系统提示**，它与缓存的系统提示结合形成最终的系统消息。框架的固定不变式是：系统提示在每个会话中只构建一次（缓存在 `_cached_system_prompt` 上），然后在每个turn中逐字重放。这样字节稳定，上游提示缓存保持热度。

### 3.4 多模态内容处理

对于多模态内容（文本 + 图像），框架会提取可见文本而不是将 Python 对象的字符串表示拼接到聚合提示中（这会泄漏 base64 图像载荷）。对于 MoA（Mixture of Agents）场景，MoA 上下文作为尾部文本部分追加，而不是静默丢弃。

### 3.5 Anthropic 提示缓存

对于支持 Anthropic 提示缓存的模型，框架会自动注入缓存控制断点（系统提示 + 最近 3 条消息），可以在多轮对话中将输入 token 成本降低约 75%。这是通过检测 `_use_prompt_caching` 标志实现的。

### 3.6 安全网：清理孤立工具结果

在发送 API 请求前，框架会无条件地剥离孤立工具结果或为缺失结果添加存根。这不是由上下文压缩特性开关控制的，因此可以捕获会话加载或手动消息操作导致的孤立问题。

### 3.7 纯思考消息的处理

框架会删除只有推理（thinking）没有可见输出也没有工具调用的助手消息，并合并相邻的用户消息。这防止了某些第三方 Anthropic 兼容网关在重放会话时可能出现的 400 错误（"The final block in an assistant message cannot be thinking"）。

此操作仅在每次调用的副本上运行，存储的对话历史保留推理块以用于 UI 记录和会话持久化。

### 3.8 前缀匹配的规范化

框架会规范化消息空格和工具调用 JSON 以实现一致的前缀匹配。这确保了跨turn的位精确前缀，从而支持本地推理服务器（llama.cpp、vLLM、Ollama）上的 KV 缓存重用，并提高了云 provider 的缓存命中率。

### 3.9 Unicode 净化

在 API 调用前，框架会主动剥离任何代理字符。通过 Ollama 提供的模型（Kimi K2.5、GLM-5、Qwen）可能返回孤立的代理字符（U+D800-U+DFFF），这会导致 OpenAI SDK 内部的 json.dumps() 崩溃。

## 四、预API压力检查

### 4.1 问题的引入

turn 前言的前置检查只看到传入的用户消息，但单个turn可能因多个大型工具结果而增长，在下一次调用前没有输出预算。响应后的 `should_compress` 门使用 API 报告的 `last_prompt_tokens`，但它滞后于刚附加的大型工具结果，因此会错过这种情况。

### 4.2 解决方案

框架在 API 调用前重新检查当前请求估计值，镜像 turn 前言的前置检查链：当粗略估计已知相对于最近的真实 provider 提示有噪声时推迟；当同一会话的压缩失败冷却期间活跃时跳过；然后调用 `should_compress()`。

## 五、API调用与响应处理

### 5.1 流式优先策略

框架始终优先使用流式路径，即使没有流式消费者。流式提供了细粒度的健康检查（90秒流过期检测、60秒读取超时），而非流式路径缺乏这些。对于子代理和其他安静模式调用者，当 provider 保持连接活动但从不传递响应时，可能会无限挂起。

### 5.2 响应验证

在处理响应前，框架会验证响应形状。如果 provider 返回终端失败（如配额耗尽），则将其视为无效以触发备用链，而不是让错误气泡到重试/备用循环之外。

### 5.3 内容策略拒绝

当模型或 provider 的安全系统返回成功响应但停止原因是拒绝时（Anthropic 的 `stop_reason="refusal"` → `content_filter`），框架会识别这种情况并正确处理。内容通常为空，如果没有这个分支，响应会落入空响应/无效响应重试循环，被误标为"速率限制"或"重试后无内容"。

### 5.4 响应截断处理

对于被截断的响应，框架会将截断的响应规范化为单个 OpenAI 风格的消息形状，使文本继续和工具调用重试在 chat_completions、bedrock_converse 和 anthropic_messages 之间均匀工作。

### 5.5 思考预算耗尽检测

当模型将所有输出 token 都花在推理上而没有剩余用于响应时，框架会提前检测并提供有针对性的错误，而不是浪费 3 次 API 调用。只有当模型实际产生了推理块但它们之后没有可见文本时，响应才被认为是"思考耗尽"。

### 5.6 令牌使用跟踪

框架跟踪响应的实际令牌使用以进行上下文管理。MoA 场景下，框架会将引用（advisor）扇出的令牌使用合并到此 turn 报告的令牌计数中。MoA 在 aggregator 之前运行 advisor 并只返回 aggregator 的使用，如果没有这个合并，整个 advisor 支出（通常是 MoA turn 的主体）在令牌计数中是不可见的。

## 六、错误恢复机制

### 6.1 Unicode编码错误恢复

框架处理两种常见的 Unicode 编码错误：

**第一种是孤立代理字符**，来自剪贴板粘贴（Google Docs、富文本编辑器）。解决方案是净化并重试。

**第二种是 ASCII 编解码器**，在使用 LANG=C 或非 UTF-8 语言环境的系统上，任何非 ASCII 字符都会失败。解决方案是检测编解码器错误并净化所有非 ASCII 内容。

框架在消息中就地净化，并可能重试两次：第一次剥离代理字符，第二次如果需要则进行纯 ASCII 语言环境净化。

### 6.2 图像拒绝恢复

某些 provider（mlx-lm、文本端点、多模态模型的文本回退）会拒绝包含 image_url 内容的任何消息。在首次命中时，框架会从消息列表中剥离所有图像，将会话标记为不支持视觉，并使用纯文本重试。

对于特定 provider 还有特殊处理：ChatGPT 账户的 Codex 后端拒绝 data:image/...base64 URL；DeepSeek 的 OpenAI 兼容 API 将纯文本请求体变体报告为"unknown variant `image_url`, expected `text`"；OpenRouter 当候选端点都不支持图像输入时返回 HTTP 404。

### 6.3 思考块签名恢复

Anthropic 对思考块进行签名以对抗完整的内容。任何上游变更（上下文压缩、会话截断、消息合并）都会使签名无效，API 会回复 HTTP 400（"invalid signature"或"cannot be modified"）。恢复方案是剥离 `reasoning_details` 以便重试不发送任何思考块。

### 6.4 无效加密推理重放恢复

OpenAI Responses API 和某些兼容中继在重放先前turn的 `codex_reasoning_items` blob 失败验证时返回 HTTP 400 `invalid_encrypted_content`（provider 轮换了加密密钥、路由实际上不保留推理状态等）。恢复方案是禁用会话其余部分的重放，从历史中剥离缓存项目，并重试一次。

### 6.5 llama.cpp 语法解析恢复

llama.cpp 的 json-schema-to-grammar 转换器拒绝工具模式中的正则转义类（`\d`、`\w`、`\s`）和大多数 `format` 值。MCP 服务器经常为日期/电话/邮箱参数发出这些。恢复方案是从 `agent.tools` 中剥离 `pattern`/`format` 并重试一次。

### 6.6 上下文溢出处理

对于 413 负载过大错误，正确的响应是压缩历史并重试，而不是立即中止。但当用户禁用了自动压缩时，框架会尊重该设置并显示终端错误，而不是静默压缩和轮换会话。

### 6.7 Anthropic Sonnet 长上下文层门

Anthropic 返回 HTTP 429 "Extra usage is required for long context requests"，当 Claude Max 或类似订阅不包含 1M 上下文层时。这是瞬时速率限制，重试或切换凭证无济于事。框架会将上下文减少到 200k（标准层）并压缩。

### 6.8 速率限制与备用切换

对于速率限制错误（429 或配额耗尽）和传输错误（连接失败/超时/provider 过载），框架采用不同的策略。速率限制和计费立即切换，因为主要 provider 在重试窗口内不会恢复；传输错误先允许 1 次重试，然后如果 provider 确实无法访问则回退。

### 6.9 认证失败 Provider 故障转移

当 401/403 在每个 provider 的凭证刷新尝试后仍然存在时，意味着活动 provider 的凭证或端点以刷新无法修复的方式损坏（撤销的 OAuth、过期/阻止的密钥、绑定到死/暂存端点的账户）。框架会升级到备用链。

### 6.10 Nous Portal 速率限制

当 Nous 返回真正的账户级速率限制时，框架会将重置时间记录到共享文件中，以便所有会话知道不要堆积，然后跳过进一步重试。每个尝试都会消耗另一个 RPH 请求并加深限制孔。

## 七、会话持久化与状态管理

### 7.1 系统提示缓存

系统提示在 SQLite 中持久化。之前失败时只在 DEBUG 级别记录，这会静默破坏网关路径上的前缀缓存重用。

### 7.2 令牌计数持久化

每个 API 调用的令牌计数都会持久化到会话数据库以供分析使用。框架为每个平台执行此操作，这样非 CLI 会话（gateway、cron、委托运行）如果更高级别的持久化路径被跳过或失败，就不会丢失令牌/会计数据。

### 7.3 缓存命中率显示

框架会显示任何报告缓存命中的 provider 的缓存命中率统计，而不仅仅是那些我们注入缓存控制标记的 provider。OpenAI/Kimi/DeepSeek/Qwen 都做自动服务器端前缀缓存并返回 `prompt_tokens_details.cached_tokens`。

## 八、特殊机制

### 8.1 /steer 指令的时序处理

`/steer` 指令允许用户在对话过程中动态调整模型行为。如果用户在模型思考时（API 调用进行中）发送 steer，没有特殊处理的话，steer 会等到下一次 API 调用才生效。框架的解决方案是在下次 API 调用之前将 steer "排出"到最后一个 tool-role 消息之后。

### 8.2 等待验证的响应

框架会保留被验证门故意扣留的最后一个组合答案。如果该延续消耗了剩余预算，这是面向用户的最佳可用结果，必须不能与无关退出路径产生的错误或恢复文本混淆。

### 8.3 截断工具调用重试

框架会在每次重试时增加 max_tokens，以便模型有更多空间完成工具调用 JSON。网络stall不需要更大的预算，但真正的输出截断需要，增加对 stall 情况无害。

## 九、架构设计要点

### 9.1 副本策略

框架广泛使用"副本"策略：原始数据保持不变，所有临时性的修改和清理都在副本上进行。这使得原始数据可用于调试、UI 显示和会话持久化，同时 API 调用可以自由转换。

### 9.2 防御性编程

每个可能出错的地方都有对应的恢复逻辑。从简单的空响应重试到复杂的签名无效恢复，框架尽力确保即使在异常情况下也能产生有意义的输出。

### 9.3 Provider 适配

框架需要适配多种 API provider（Anthropic、OpenAI、OpenRouter、Bedrock、Ollama 等），每种都有不同的 API 形状和限制。代码中大量的 provider 特定处理反映了这种复杂性。

### 9.4 预算管理

迭代预算和宽恕调用的设计确保了资源使用的可预测性，同时在预算紧张时仍能产生有用输出。

## 十、总结

`run_conversation` 方法是 Hermes Agent 框架中最复杂的组件之一，它展示了构建生产级 Agent 系统所需考虑的各种边界情况。从消息预处理到错误恢复，从会话持久化到多 provider 适配，每个设计决策都源于实际使用中的问题。

理解这些机制不仅有助于维护和扩展该框架，也为构建其他 Agent 系统提供了宝贵的参考。核心原则是：保持原始数据不变、在副本上操作、为每种可能的错误准备恢复逻辑、支持多种 provider 和运行时模式。
