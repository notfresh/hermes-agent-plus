## 三、为什么值得这么长？—— 五层装甲，每层对应一类真实事故

### 第 1 层：API 调用与重试（约 1500 行，最大块）

核心循环里"调 API"只有一行，但真实世界里 API 会：
- 超时（网络抖动）
- 429 限流
- 5xx 服务端错误
- 连接被掐断
- 返回畸形 JSON
- 返回空响应

**每个都要：检测 → 分类 → 决定重试还是放弃 → 退避等待 → 记录日志。**
这就是 469 行提到 retry/backoff 的原因。教学 demo 里 `requests.post()` 一行搞定；生产代码里这一行要膨胀成 1500 行——因为**用户的请求不能因为一次网络抖动就失败**。

### 第 2 层：错误分类处理（约 500 行）

注意 :4200 那个专门分支——**"模型思考超时"单独一个处理块**。这是 reasoning 模型（DeepSeek 这类）在云网关后面特有的坑：模型思考阶段超过上游 idle 超时，第一个 token 迟迟不来。这段代码不仅检测错误，还**给用户打印 3 条解决方案**（改配置、降 reasoning、换模型）。

为什么要写这么细？因为普通报错信息"request timed out"让用户无从下手；而这段代码把**已知问题 + 解决方案直接打印给用户**。这是真实产品踩出来的经验。

同类分支还有：billing 耗尽（:4252）、413 请求太大（:3596）、上下文超长（:3826）……**每种错误一个专门分支，每个分支都可能 100+ 行**。

### 第 3 层：上下文压缩（约 400 行）

对话越来越长 → 超过模型上下文窗口 → 必须压缩。但压缩本身也会失败：
- 压缩后还是太长（:3540 上限）
- 请求 413 无法压缩（:3596）
- 压缩重试（:3781）
- 最终放弃（:3826）

这 400 行全是为了处理"对话太长"这一个问题。教学 demo 根本不需要——但真实 agent 跑 100 轮对话后一定会撞上。

### 第 4 层：凭证/fallback（约 340 行）

API key 过期、被限流、provider 挂掉 → 自动换凭证、换 provider。这也是为什么你能看到 340 行提到 fallback/credential/token。

### 第 5 层：工具调用防御（约 300 行）

模型可能"编造"不存在的工具（:4764 非法 tool call）、工具参数格式错、工具执行超时……都要处理。

- 发动机原理：进气→压缩→燃烧→排气，4 步，10 行能写完
- 但一辆能上路的车需要：方向盘、刹车、ABS、气囊、空调、安全带、倒车雷达、安全气囊……每个系统都是"原理上可有可无，实际上必须有"

## 五、那为什么不拆开？—— 两个真实原因

1. **状态耦合**：这些防御块共享大量局部变量（api_call_count、messages、final_response、各种重试计数），拆出去要传十几个参数，反而更难读
2. **没人有空拆**：每天 43 次提交的节奏下，拆文件这种"不增加功能"的重构永远排不上队（AGENTS.md 自己都承认这是 wanted work）
