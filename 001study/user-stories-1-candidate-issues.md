## 故事一：前台小姐的"自动转接"事故（#79788 fallback URL 重写）

### 场景
想象 Hermes 是一个公司的前台小姐。她有一部主电话（你的主力模型 provider），还有一部备用电话（fallback provider）——主电话坏了就用备用，这是公司定的规矩。

某天主电话真坏了。前台小姐按规矩抓起备用电话，但她在拨号前**习惯性地把电话号码改成了自家格式**——备用电话明明是另一家运营商（Anthropic 兼容的），她却不管三七二十一，把它的号码也格式化成"本公司格式"（把 `/anthropic` 后缀改成 `/v1`）。

结果：备用电话**通了**，但对面听不懂她的格式，所有通话全部失败。

### 主角的遭遇
用户配好了 fallback（主 provider 挂了自动切到 Anthropic 兼容的备用），平时风平浪静。直到某天主 provider 真挂了——系统"成功"切换到了备用，但**切换后的请求全部失败**。用户查日志，发现 URL 被改写成了 `/v1` 而不是 `/anthropic`，一脸懵："它明明连上了，为什么不工作？"

### 原理大白话
- 代码里有个工具函数叫 `_to_openai_base_url`（"转成 OpenAI 格式的 URL"）。它的名字和注释都**假设**所有调用者都走 OpenAI 那套协议——这就是"隐藏假设"。
- fallback 激活路径上，这个函数被无条件调用，把 Anthropic 的 `/anthropic` 后缀也重写了。
- 更妙的是：URL 被改写**之后**，系统才根据 URL 推断该用哪套协议——推断逻辑看到 `/v1` 就以为是对面 OpenAI，一步错步步错。顺序敏感。

### 一句话
**一个 helper 函数的"想当然"，让整条 fallback 链路在关键时刻失灵。**

## 故事二：同一份菜单，两个厨师一个找得到菜、一个说"没这道菜"（#84667 cron skill 加载）

### 场景
你开了家餐厅。后厨有两位厨师：一位是"点单厨师"（CLI），一位是"定时厨师"（cron 任务，每天定时做菜）。你给定时厨师一张菜单，上面写着"燕麦粥（早餐）"。

奇怪的事发生了：点单厨师喊"燕麦粥"——食材库里有，顺利开做。定时厨师喊"燕麦粥"——食材库明明也有，他却说"没找到这道菜，跳过"。**同一份菜单、同一个食材库，两个人的结果不一样。**

（今天的剧情更新：有位热心食客 @1deat0r 仔细查了后厨，发现两位厨师**其实走的是同一个找菜流程**——所以问题比"两个人流程不同"更深，是某个环节对"菜名"的写法/匹配方式不一样。而且"报错说没找到"这个表面问题，已经有人开始修了。）

### 主角的遭遇
用户给 cron 任务配置了 `skills: [xxx]`，任务跑起来后 agent 说 "skill not found, skipping"（技能没找到，跳过），但用户明明装了那个 skill，CLI 里也能正常用。定时任务因此"带病运行"——该用的技能没用上。

### 原理大白话
- 这个 issue 今天（08-15）**变天了**：@1deat0r 的深度调查纠正了大家对根因的理解（不是两条路径不一致，而是同一路径上某处查找键/名字规范化的问题）；同时"报错信息太模糊"这部分已被 PR #73453 认领。
- 它从"可以下手的小修复"变成了"根因待定 + 部分被认领"——**不再适合推荐做**，但过程本身是绝佳教材：**一个 issue 的定义如何在几小时内被评论改写**。这正是我们学的"写方案前必须读最新评论"的活例子。

### 一句话
**你以为的 bug 根因，可能是别人一句评论就能推翻的。**

## 故事三：满墙的水龙头（#84233 state.db 连接泄漏）

### 场景
Hermes 有个监控面板（dashboard），像你家的洗手台。洗手台上装了一排水龙头（数据库连接），规矩是**用完一个关一个**。

但某个版本开始，水龙头坏了：每次刷新页面、每次操作，都**新开一个水龙头，旧的不关**。你平时不看，无所谓。跑了两三天后，你回家一看——整面墙密密麻麻全是水龙头（文件描述符达到系统上限 256 个）！新水管工想接新管子，发现墙上没有空位了（"Too many open files"），整个系统罢工。

macOS 用户 @TheOpie 还发现：就算没人在看面板，只要它挂在后台（launchd 启动），水龙头也在悄悄变多——**后台常驻 + 偷偷泄漏**，是最阴的组合。

### 主角的遭遇
用户 dashboard 开久了，突然所有功能开始报 "Too many open files"，重启 Hermes 才能恢复。几天后又复发。查了半天发现是 state.db 的连接只开不关。

### 原理大白话
- 资源泄漏的经典模式：**获取连接的路径有很多条，释放连接的路径却漏了一条**（比如某条分支 return 时忘了 close）。
- 长尾进程（dashboard 常驻）最容易暴露这种 bug——短命令进程用完就退出，泄漏随进程死亡被"冲走"；常驻进程的泄漏会累积到爆炸。
- 注意：这个 issue 的 reporter @TheOpie 本人正在跟进（亲自复现、贴证据），**撞车风险高**——这也是我们盯盘的重点。

### 一句话
**后台常驻进程的资源泄漏，是"温水煮青蛙"式的慢性死亡。**

## 故事四：助手的"8 秒魔咒"（#85135 memory 8s 硬编码）

### 场景
你的助手（Hermes）有个"记忆图书馆"（外部 memory provider，比如 Honcho）。你在这台电脑上让助手记住的事，存在图书馆里；在别的设备上问它，它去图书馆调档案。

图书馆调档案有快有慢：平时 3 秒送到，但**冷启动**（很久没人调书，书库要重新点火）要 9~11 秒。

助手给自己定了一条死规矩（硬编码在代码里）：**任何调书请求，8 秒没送到就放弃**。于是——你明明在别的设备上让助手记住了"下周三是妈妈生日"，这边问它，它等 8 秒没等到，就说"没查到"。你：？？？我刚告诉过你的啊！

### 主角的遭遇
用户配了外部 memory（Honcho），冷调用经常超时被砍，记忆时灵时不灵。用户想改超时时间——翻遍配置，**根本没有这个选项**。因为代码里写死了 8 秒。

### 原理大白话
- 最气人的是：代码里 `MemoryManager.__init__` **早就预留了** `external_prefetch_timeout` 参数（有校验、有默认值），但实例化的时候**从来不传**——参数成了摆设。
- 这是经典模式："**能力存在，路径没连通**"。修起来可能就一两行（把配置接进去），但找出来要读完整条初始化链路。
- 为什么是 P3 低危？因为只有配了外部 memory 的用户才受影响，且是"慢"不是"错"。

### 一句话
**写死的常量 + 没人接线的参数 = 用户想调都调不了的坑。**
