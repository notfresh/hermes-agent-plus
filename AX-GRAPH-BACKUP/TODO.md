# AX-GRAPH 待办规划 — 行号漂移的辅助手动更新

> **背景**：图里的 `path` 行号是时间快照，源码一更新就漂移（教训：`skill_commands.py` 的 `_load_skill_payload` 曾 725→138）。
> **现状**：`--validate` 能**发现**漂移（✗ 行号不是 def/class），但没有**建议**手段；修要人工 grep + 手改 TOML。
> **目标**：把「发现 → 建议 → 手动确认 → 验证」闭环工具化。
> **第一原则（不可推翻）：人在回路，且更新必须配合阅读和理解代码的过程。** 更新图**不是禁止 AI 参与**——AI 完全可以做：发现漂移、AST 给建议、按指挥执行修改。但**必须有人指挥**：人发起 → AI 报告建议 → 人确认 → AI 执行 → 人验证。**而且更新永远不是"改个数字"**：改行号/改节点时，必须伴随阅读和理解该函数的当前代码——确认函数还在吗、语义变了吗、上下文是什么。反对的是两种模式：①拉取代码后脚本全量自动重建（无人在循环，偷走学习过程）；②机械更新（不看代码直接改数字，哪怕数字来自 AST 建议）。**改图 = 读码的副产品，不是独立的机械操作。**
> **推进顺序（已定）**：单点建议 → 指定 function 列表报告 → AST 全量漂移报告。一步一步来，先跑通单点再扩批量。

---

## 阶段一：单点漂移建议（最先做）

- **命令形态**：`python3 graph_query.py --suggest <节点id>`
- **功能**：AST 解析该节点所在文件 → 按「文件::函数名」查当前实际行号 → 输出：
  ```
  节点: func.xxx.yyy  path= ./agent/foo.py:725  ✗ 行号漂移
  AST 查到: agent/foo.py:138  (def yyy)
  ```
- **不写盘**。人看到建议后，手改 TOML（或复制新行号）。
- **匹配不到**（函数被删 / 改名 / 文件移动）→ 报"孤儿"，提示可能函数已删/改名，需人工读码确认
- **配套**：`--validate <id>` 报"行号不是 def/class"时，末尾追加一行提示"可运行 --suggest <id> 查建议"
- **验收**：validate 报漂移的节点，`--suggest <id>` 给出准确新行号建议；人按建议手改后 0 错
- **依赖**：AST 提取复用 `call_candidates.py` 已有基础设施（不新造轮子）

## 阶段二：指定 function 列表漂移报告

- **命令形态**：`--suggest <id1> <id2> ...`（命令行多个）或 `--suggest --from <列表文件>`（每行一个 id）
- **功能**：批量生成漂移报告（对照表）：
  ```
  ┌─ 行号漂移报告（4 个节点）────────────────
  │ func.a.b   725 → 138   ✓可定位
  │ func.c.d   431 → ?     孤儿：文件内未找到 def d
  │ func.e.f   (无变化)     仍为 512
  └────────────────────────────
  ```
- **只报告不写盘**；人按报告逐条手改
- **输出**：`可定位 N / 孤儿 M / 无变化 K`
- **验收**：列表内节点全部按报告手改后 validate 0 错；孤儿清单准确

## 阶段三：AST 全量漂移报告

- **命令形态**：`--suggest --all`（全图扫描）
- **功能**：扫描全图所有 function 节点 → AST 全量提取文件内 def/class 行号 → 生成全量漂移报告（含孤儿清单）
- **范围控制**：可配 `-l N`（只看某层）
- **孤儿集中报告**：函数删除/改名/文件移动的全部列出，人工决定（改 id / 删节点 / 标待验证），**工具不自动处理**
- **验收**：全量报告可审计；按报告手改后 `--validate` 0 行号错误

---

## 通用设计要点（三阶段共用）

1. **匹配策略：AST 优先，不做 grep 文本匹配**——精确支持 async def / 类方法；同文件同名函数列出候选行号人工确认
2. **孤儿处理：显式报告，不静默跳过，不自动删除**——行号漂移可能意味着函数真的没了，那是图结构问题不是行号问题
3. **`--suggest` 只读不写**——工具只报告建议；落盘修改由人确认后执行（人直接改，或人指挥 AI 改）。工具层绝不自主写盘
4. **与 validate 闭环**：`git pull → --validate（发现漂移）→ --suggest（拿建议）→ 人确认 + 读码理解 → 修改（人手或指挥 AI）→ --validate（0 错）`
5. **更新必须配合阅读和理解代码**：改行号/改节点时，必须读该函数当前源码——确认函数还在、语义变化、上下文如何。这不是负担，是更新的意义本身：图是读码的副产品。**AI 执行更新时同样要先读代码再改**，禁止"不看代码直接改数字"（哪怕数字来自 AST 建议）——那是机械更新，同样是错的
6. **行号当次实测铁律不变**：`--suggest` 是"当次实测"的辅助形态，最终落盘的仍然是人工核实的行号
