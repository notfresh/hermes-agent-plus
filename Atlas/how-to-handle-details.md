# 如何处理工程细节

> 核心原理 vs 工程细节的判断与学习策略

---

## 一、核心原理与工程细节的区别

### 核心原理（必须掌握）

- **特征**：不变的思想、模式、架构
- **例子**：
  - Agent 核心循环：`Message → LLM → Tool → Loop`
  - 工具调用的 `finish_reason` 分支
  - 消息历史的管理
- **学习方法**：理解 + 能画出来

### 工程细节（随用随查）

- **特征**：边界 case、兼容性处理、补丁
- **例子**：
  - `_reset_stream_delivery_tracking` - 流式重试时的文本清理
  - `_reapply_reasoning_echo_for_provider` - 跨 provider 回退兼容性
  - think scrubber / context scrubber
- **学习方法**：遇到时再查，不需要背

---

## 二、如何判断一个代码是不是"工程细节"

### 判断标准

| 问题 | 答案 |
|------|------|
| 这是核心业务流程的一部分吗？ | 否 → 很可能是细节 |
| 去掉了代码还能跑吗？ | 能 → 很可能是细节 |
| 这是为了处理某个边界 case 吗？ | 是 → 很可能是细节 |
| 这个逻辑在面试中会被考察吗？ | 否 → 很可能是细节 |

### 常见工程细节类型

1. **Provider 适配** - 不同 LLM API 的字段差异、兼容处理
2. **重试逻辑** - 失败后的补偿机制
3. **流式处理** - 文本片段的组装、清理
4. **错误恢复** - 崩溃后的 WAL 恢复
5. **性能优化** - 缓存、压缩、预算控制
6. **边界 case** - 空消息、角色错乱、截断

## 三、正确的学习路径

```
第一层：核心原理
    ↓
  理解 Agent 循环、能画流程图
    ↓
第二层：模块认知
    ↓
  知道有哪些模块、各自负责什么
    ↓
第三层：细节攻坚
    ↓
  在实践中逐个攻克工程细节
```

## 四、遇到细节代码怎么办

### 不要

- ❌ 试图一次性理解所有细节
- ❌ 死记硬背
- ❌ 被吓住觉得自己不行

### 要

- ✅ 先理解这段代码"修什么 bug"
- ✅ 关联到具体的使用场景
- ✅ 用到时再深入
- ✅ 善用 git blame 追溯历史

### 查找技巧

```bash
# 搜索相关代码
grep -n "关键词" run_agent.py agent/*.py

# 追溯历史（这个 bug 从哪来）
git blame -L 行号,行号 文件

# 搜索相关 issue
grep -r "issue\|bug\|fix" --include="*.py" | grep "关键词"
```

## 五、真正的能力是什么

| 能力 | 说明 |
|------|------|
| **快速定位** | 遇到问题知道去哪找代码 |
| **快速理解** | 代码摆在那儿，能读懂它在修什么 |
| **举一反三** | 这个 patch 的思路能不能用到其他地方 |

> 细节是**记忆力**的差距，原理是**理解力**的差距。前者查文档就行，后者才是真正的能力。

---

## 六、实战建议

1. **先跑通核心循环** — 用简化版代码跑通基本流程
2. **遇到问题再深入** — 不要提前学所有细节
3. **每解决一个 bug** — 就理解了一个工程细节
4. **定期复盘** — 把解决的细节写成笔记
