# Spec: `-xz` / `-zx` — Oneshot with Session History

## Overview

Add a new invocation mode `hermes -xz` (and its synonym `hermes -zx`) that combines the
stateless, silent, single-response behaviour of `hermes -z` with the full conversation
history of the most recent CLI/TUI session.  It is designed as the scripting-friendly
equivalent of `hermes -c` — identical output contract to `-z` but with contextual
continuity.

```
hermes -xz "continue refining this function"   # load last session history, send prompt
hermes -zx "continue refining this function"   # identical; -xz and -zx are synonyms
hermes -z  "one-off question"                  # unchanged; no history, no session
```

## Behaviour

| Property | `-z` | `-xz` / `-zx` |
|---|---|---|
| Banner / spinner | no | no |
| Session history loaded | no | yes (most recent CLI/TUI session) |
| Output format | final text block only | final text block only |
| Exits to shell after response | yes | yes |
| TUI / interactive loop | never started | never started |
| Works in scripts / pipes | yes | yes |
| YOLO mode (auto-approve tools) | yes | yes |
| Usage file (`--usage-file`) | supported | supported |
| `--model` / `--provider` / `--toolsets` | supported | supported |

### Exit codes

| Scenario | Exit code |
|---|---|
| Normal completion | 0 |
| No recent session found | 2 |
| `--provider` given without `--model` | 2 |
| Bad `--toolsets` | 2 |
| Agent raised an exception | 1 |
| No final response produced | 1 |

Error messages are written to stderr and are prefixed with `hermes -xz:` so pipelines
can distinguish them from stdout content.

## User interactions

```
# First session (new problem)
hermes -z "explain asyncio"

# Continue that conversation from the shell (no TUI)
hermes -xz "now show a concrete example"

# Shorthand synonym
hermes -zx "add error handling"
```

If there is no prior CLI/TUI session (empty `sessions` table), `hermes -xz` fails with:

```
hermes -xz: no session found to resume
```

## Design

### 1. Parser changes — `hermes_cli/_parser.py`

A new mutually-exclusive group is added to the top-level parser containing `-z` / `--oneshot`
and `-xz` / `--zx`:

```
group = parser.add_mutually_exclusive_group()
group.add_argument("-z", "--oneshot", dest="oneshot", metavar="PROMPT", default=None, ...)
group.add_argument("-xz", "--xz", dest="xz", metavar="PROMPT", default=None, ...)
group.add_argument("-zx", "--zx", dest="xz", metavar="PROMPT", default=None, ...)
```

Both `-xz` and `-zx` write to the same `args.xz` field.  `args.oneshot` and `args.xz`
are never both non-None.

### 2. Dispatch changes — `hermes_cli/main.py`

In `main()`, the existing oneshot branch is extended:

```python
if getattr(args, "xz", None):
    from hermes_cli.oneshot import run_oneshot_with_session
    sys.exit(run_oneshot_with_session(
        args.xz,
        model=getattr(args, "model", None),
        provider=getattr(args, "provider", None),
        toolsets=getattr(args, "toolsets", None),
        usage_file=getattr(args, "usage_file", None),
    ))
elif getattr(args, "oneshot", None):
    from hermes_cli.oneshot import run_oneshot
    sys.exit(run_oneshot(...))   # existing path unchanged
```

`run_oneshot_with_session` is a new function (see below).  Existing code for
`cmd_chat`, `--resume`, `-c` etc. is untouched.

Session resolution uses the existing `_resolve_last_session(source="cli")` helper.
"TUI" sessions are included by passing `source=None` so the query returns the
most recent across both channels.

### 3. New function — `hermes_cli/oneshot.py`

```python
def run_oneshot_with_session(
    prompt: str,
    model: Optional[str] = None,
    provider: Optional[str] = None,
    toolsets: object = None,
    usage_file: Optional[str] = None,
) -> int:
```

Steps:

1. **Resolve session** — call `SessionDB().resolve_last_session(source=None)` to get the
   most recent session (CLI or TUI).  If none found, print error and return 2.
2. **Load history** — call `SessionDB().get_messages_as_conversation(session_id,
   repair_alternation=True)` to get the full message list in OpenAI message-dict format.
3. **Validate history** — if the returned list is empty, treat as "no session" and fail
   with exit 2.
4. **Set YOLO / hooks** — same as `run_oneshot`: `HERMES_YOLO_MODE=1`,
   `HERMES_ACCEPT_HOOKS=1`, `declare_stateless_channel()`.
5. **Redirect stdout/stderr** — same as `run_oneshot`: redirect to `/dev/null` for the
   entire call tree, restore at the end.
6. **Call `_run_agent_with_history`** (new, see below).
7. **Write usage file** and emit final response on real stdout — same as `run_oneshot`.

```python
def _run_agent_with_history(
    prompt: str,
    session_id: str,
    conversation_history: list[dict],
    model: Optional[str],
    provider: Optional[str],
    toolsets: object,
) -> tuple[str, dict]:
```

This is a variant of `_run_agent` that passes `conversation_history` and `session_id`
to `AIAgent`.  The `AIAgent` call looks like:

```python
agent = AIAgent(
    ...,
    session_id=session_id,       # new
    session_db=session_db,        # new (SessionDB instance)
    quiet_mode=True,
    platform="cli",
    clarify_callback=_oneshot_clarify_callback,
)
result = agent.run_conversation(prompt, conversation_history=conversation_history)
```

`_oneshot_clarify_callback` is reused from the existing `-z` path.

The `session_db` passed here is a fresh `SessionDB()` instance, NOT the
`_create_session_db_for_oneshot()` lightweight handle — full persistence is desired
so the `-xz` turn is recorded as a real continuation of the session.

### 4. History injection alignment

The history loading path mirrors what `HermesCLI._preload_resumed_session()` does in
the interactive CLI (`cli_agent_setup_mixin.py:455`):

- `get_messages_as_conversation(session_id, repair_alternation=True)` — same call
- `repair_alternation=True` — same flag (handles edge cases where a prior crash left
  the message table in an alternating-role-broken state)
- The returned list is passed directly as `conversation_history` — same format the
  agent's `run_conversation` expects

The agent will append the new user turn and all assistant turns internally, then
`finalize_turn` → `_flush_messages_to_session_db` writes them back, so the session
remains consistent.

### 5. Files changed

| File | Change |
|---|---|
| `hermes_cli/_parser.py` | Add `-xz`/`--xz`/`-zx` flags in a new mutually-exclusive group with `-z` |
| `hermes_cli/main.py` | Dispatch to `run_oneshot_with_session` when `args.xz` is set |
| `hermes_cli/oneshot.py` | Add `run_oneshot_with_session()` and `_run_agent_with_history()` |

No changes to `cli.py`, `run_agent.py`, `SessionDB`, or any agent core files.

## Open questions (resolved)

**Q: Should `-z` and `-xz` be mutually exclusive?**
A: Yes.  They are distinct modes with different semantics.  Attempting to combine them
is an error and argparse enforces this at parse time.

**Q: How is the session found?**
A: `_resolve_last_session(source=None)` — the most recent session across CLI and TUI
channels.  Falls back to `resolve_last_session(source="cli")` if the combined query
returns nothing.

**Q: What if there are no prior sessions?**
A: Exit 2 with `hermes -xz: no session found to resume`.

**Q: Does `-xz` write back to the session?**
A: Yes.  The new user turn and agent response are persisted to the session via the
standard `_flush_messages_to_session_db` path, so the session grows naturally.

**Q: Are `--usage-file`, `--model`, `--provider`, `--toolsets` supported?**
A: Yes, all passed through identically to `run_oneshot`.

**Q: Is there a way to specify a non-latest session?**
A: Not in this initial spec.  Future extension could add `--xz-session <id>` or similar.
